# AI 自动申诉稳定性

## 行为与边界

- “客服模式”只负责选择 AI 客服或人工客服，不包含 AI 话术选项。自动化 AI 申诉和任务模块都有独立的“话术模式”（普通模式 / AI话术模式）。普通模式不调用 DeepSeek；AI话术模式仅对侵权和禁限售生效：按产品编号读取 Mercado Libre 标题和描述，再用本次手动填写的 DeepSeek Token 生成有事实依据的理由。每组最多 3 个产品，理由正文不超过 50 个字符；Token 不写入申诉记录、任务历史或运行日志。只有明确的站点选择问题才自动回复本地站点名称，最多两次，其他客服回复原样记录。
- 人工客服入口提交初始申诉后保留页面，交由用户继续沟通。
- 申诉期间检测到 Mercado 登录失效时，只执行一次自动登录；成功后继续当前申诉，失败立即记录登录异常、关闭完整 BitBrowser 窗口，并终止当前店铺本轮后续站点和任务。
- 重复申诉、原有轮次和类型顺序保持不变；未增加业务去重或冷却时间。任务模块的店铺并发同时受 `BIT_DAILY_BROWSER_WORKER_LIMIT` 和 `BIT_BROWSER_MAX_OPEN_WINDOWS` 限制，避免过多进程等待浏览器窗口槽位而超时。
- 确认点击聊天窗口的发送按钮后即记为“话术发送成功”；不等待消息回显、输入框清空或客服回复，且发送成功不代表平台批准申诉，业务结果仍需在平台核实。

## 执行可靠性

发送按钮点击成功后立即记为 `sent`，并将本次实际话术和话术模式写入自动化申诉记录；通过回车兜底发送时仍检查消息回显和输入框状态。只有发送前的普通异常才有限重试。发送成功后仍会等待并保存客服回复，但回复超时、站点追问或后续读取异常只作为附加信息，不会撤销发送成功状态。

消息读取覆盖 iframe 和内嵌聊天的已知结构（含开放的 Shadow DOM），用消息标识、会话标识和文本变化识别新回复；文本稳定且生成指示结束后才采用。列表缩短、相同文本的新消息都不再依赖简单的消息条数判断。没有平台消息 ID 的结构使用 DOM 节点标识；整批重建节点的第三方页面仍可能需要适配。

每组开始前校验站点。每三组更换会话，超时/发送不确定等异常后的下一组也要求新会话；无法确认新会话时停止该组发送并记录失败，不自动转入人工客服入口。

等待与分组间暂停检查停止信号和单站点预算，数据库连接/读写、页面加载和脚本均有超时。该预算是协作式检查，不是强制终止底层调用的硬超时。结束时清理日志收集状态、驱动服务和自持有的窗口锁。

任务返回结构化执行状态：新记录发送确认后为 `sent`；兼容旧记录的 `replied`。发送未确认或发送前失败仍使用 `sent_unknown`、`pre_send_failed`、`failed`、`partial`、`no_data`、`stopped`、`deadline_exceeded`、`window_busy`、`login_required`、`rate_limited`。客服回复情况记录在 `reply_status`、`reply_received`、`response` 等附加字段中。

## 日志与数据库恢复

数据库只读 GET/HEAD 请求遇到连接中断或 HTTP 500/502/503/504 时最多尝试 3 次，间隔 1、2 秒；POST 等写请求不自动重放。HTTP 401/403 单独识别为鉴权异常，整轮任务立即退出，不再每 3 分钟重复失败。服务端心跳继续向已结束但仍有旧执行进程的任务下发停止信号，不恢复其数据库访问权限。

站点快速切换只点击可见的站点选项，并且每次只点击一次。无切换器的 Help 页面不再按整页国家名称寻找可点击元素，随后沿用 cookie 切换和严格站点校验。

聊天事件先写本地 JSONL（跨进程文件锁、原子轮转、刷新到磁盘），再进入有界异步数据库队列。聊天快照不再截断为最近 20 条，并保留用户与客服双方的角色、消息 ID 和完整文本；重叠快照会按会话合并后同步写入分组/站点汇总记录的 `chat_json`。分组/站点汇总也先写本地，再尝试数据库写入。主日志写失败时尝试独立 recovery 文件；两者均失败会输出错误，不触发重新提交申诉。

数据库首次使用时按进程懒初始化，并使用 MySQL 服务端锁协调多进程建表和升级。两个申诉日志表新增可空 `event_id` 和唯一索引；用于日志补写去重，**不限制重复申诉**。数据库账号需要相应 CREATE/ALTER 权限。

数据库故障后可补写本地日志（包括轮转与 recovery 文件）。从项目根目录运行，默认只预览；确认后加 `--apply` 才写数据库：

```powershell
python -m bit.replay_appeal_logs bit/ai_chat_records.jsonl
python -m bit.replay_appeal_logs bit/ai_chat_records.jsonl --apply
```

可显式传入多个文件路径。只补写带事件 ID 的新格式日志，旧日志跳过；重复执行不会插入同一事件的多份记录。该工具仅补写日志，不提交申诉。进程被强制关闭后异步队列可能未排空，需按此方式补写；当前不自动回放或自动恢复任务。

## 配置与启用

任务模块将算法模式独立为“普通模式/算法模式”选择；普通模式下才选择混合任务或单项任务。算法模式可用于单轮或循环执行，也支持本机 Agent。每轮实时读取授权站点的普通侵权列表，并读取一次最新声誉快照；只合并超过各项执行标准的侵权、延误率、投诉率和取消率任务，禁限售仍需单独开启。

四项指标分别除以本轮对应指标的最大值，再等权求和。综合分越高，店铺启动顺序及店铺内站点执行顺序越靠前；最低分站点权重为 1，最高分为 5，中间按比例向上取整，全体同分时均为 1。每轮重新计算。侵权只调度不同商品的小批次（普通话术最多 10 个、AI 话术最多 3 个）；声誉类任务每轮按权重安排 1–5 次，使用原有站点间隔平滑轮转，低风险站点也会执行。无数据、发送不确定或重试耗尽后，取消该站点该类型本轮剩余批次，不利用权重绕过重试限制。仍遵守授权范围、业务员或店铺组、执行门槛、并发上限、登录熔断和停止控制。日志显示站点指标、综合分、权重和批次。

环境变量默认值：`BIT_AI_SEND_CONFIRM_TIMEOUT_SECONDS=30`、`BIT_AI_SITE_BUDGET_SECONDS=7200`、`BIT_AI_GROUPS_PER_CONVERSATION=3`。AI 话术模式的 Token 必须在任务页面手动填写，不读取这里的默认值；生成后的完整发送话术通过现有 `ai_appeal_records.appeal_content` 字段留存。回复超时继续使用现有配置。请先停止已有任务并重启工作台/执行进程，确保旧进程不再运行旧代码；客户端与数据库服务端都需更新。

本次以隔离测试验证异常路径；没有向真实客服提交验证申诉。平台页面更新后仍应检查首批任务的执行状态与原始回复。
