# 容量优化与验证（2026-09-23）

本次针对中心服务支撑更多用户的前五项建议进行改造。保留旧 HTTP 接口、数据库结构和 Agent 队列；不通过增加 MySQL 最大连接数扩大负载。尚未进行 100 用户、1,000 店铺的生产混合负载验收。

## 行为和边界

1. **Agent 请求与写入**：Agent 1.2.4 运行任务时每 5–5.5 秒心跳，空闲默认 10–11 秒。停止指令可能比旧版晚约数秒收到。旧 Agent 协议兼容，服务端对同一会话/任务/元数据的重复心跳在 5 秒内复用结果；新会话、新任务、新版本立即持久化，取消标记每次请求仍查询。租约默认 15 分钟，未缩短失联保护。Windows/macOS 打包客户端须重新构建并安装才会减少 HTTP 请求；旧版立即受益于服务端减少写入。
2. **统一同步预算**：订单、历史订单、链接、侵权、禁限售的店铺协调任务共用 8 个位置，普通任务最多占 6 个，近期/手动订单优先。详情线程不嵌套占用店铺位置；API Client 的 JSON/二进制请求另共用 32 个在途位置，同一凭据最多 8 个，异常与重试等待均释放位置。上传视频、其他第三方客户端不在这个 API 预算内。预算属于每个进程，因此中心同步必须由唯一 worker 执行。
3. **分批及排队**：自动链接/侵权/禁限售每轮最多调度 8 家店铺，其余到期记录继续保留在数据库。手动请求与自动调度沿用同一同步入口和跨进程任务锁。侵权/禁限售忙碌时也持久化其他店铺的更新请求，避免直接丢弃。相同类型/店铺的在途协调任务串行；订单任务沿用现有忙碌返回和每日断点机制。
4. **查询与导出**：筛选后的链接总数缓存 15 秒，缓存键包括数据库、实际 SQL/参数及授权店铺集合，写入操作使用原有缓存失效入口。总数允许短暂延迟，明细仍查询实时数据。权限范围元数据缓存容量从 32 扩到 256；已存在的显式列、分页索引和翻页方式保留，不做大表在线 DDL。修复费用刷新 SQL 中未转义的 `%`，用真实 PyMySQL 参数绑定覆盖回归。
5. **后台导出**：六类导出（旧侵权、声誉、违规总览、权利人、禁限售、风险检查）可通过 `/api/exports` 创建持久化任务，每人最多 2 个排队/执行中任务，全局最多 100 个，由一个导出线程生成。相同人员/权限范围/URL 的在途请求合并。执行时重新鉴权，状态和下载核对创建者及当前权限/店铺范围；文件最多保留 24 小时。服务重启时将未完成的 running 导出标为错误，明确要求重新提交，queued 导出继续执行。旧同步导出 URL 保留以兼容旧页面。
6. **业务包检查**：文件大小、mtime、ctime 均不变时不重复读取源码计算哈希；首次及强制构建同步执行，之后的周期检查在后台完成，心跳继续返回上一个完整版本，构建失败保留旧版本。业务包仍以 SHA-256 校验下载内容。

## 分离部署

兼容的单进程入口仍为：

```sh
python -m bit.bit_interface --role server
```

中心服务器的源码部署可改用：

```sh
python -m bit.workbench_services
```

管理进程启动并监督两个子进程：

- Web：公网入口仍是 5000，数据库连接池默认 6；不启动中心定时调度。
- worker：只监听 `127.0.0.1:5001`，请求线程默认 16，数据库连接池默认 8；负责唯一调度器及有进程内状态的任务。

Web 将指定的任务启动、停止、状态和导出请求转发到 worker。使用共享工作台会话密钥对方法、路径、请求体、时间戳和原始访问 IP 签名。worker 验证本机来源与签名，再执行原有登录/权限校验；公网数据库请求不会因转发而获得 loopback 权限。业务 POST 不自动重试；店铺链接同步状态 GET 遇到连接错误时最多自动重试 3 次。worker 仍不可用时返回 503，用户应先检查任务状态。

两个子进程必须使用相同工作目录、`WORKBENCH_SECRET_KEY`/密钥文件、`BIT_RUNTIME_LOCK_DIR` 和固定 Agent 队列路径。管理进程以规范模块名导入工作台，避免同一进程重复加载两份任务状态。进程锁限制一个中心调度器；不应同时运行旧 combined 服务和新 worker。当前方案仅为一台主机上的 Web/worker 分离，不是多机多副本部署。

可调配置：

| 变量 | 默认 |
| --- | --- |
| `MERCADO_SYNC_STORE_BUDGET` | 8 |
| `MERCADO_SYNC_ORDER_RESERVE` | 2 |
| `MERCADO_SYNC_AUTO_BATCH_STORES` | 8 |
| `MERCADO_API_INFLIGHT_LIMIT` | 32 |
| `MERCADO_API_ACCOUNT_INFLIGHT_LIMIT` | 8 |
| `BIT_WORKER_PORT` | 5001 |
| `BIT_WEB_DB_CONNECTIONS` | 6 |
| `BIT_WORKER_DB_CONNECTIONS` | 8 |
| `BIT_WORKER_WSGI_THREADS` | 16 |

Cloudflare Tunnel 继续连接 5000，无需开放 5001。切换前检查中心正在运行的手工任务，等待合适窗口；Agent 的已入队任务保存在原固定 SQLite，不删除或迁移。

## 2026-10-08 后台进程隔离

`python -m bit.workbench_services` 现在启动五个独立进程。原单进程 `combined` 入口保留兼容；托管启动器固定启用分组，不允许误退回共享 worker。

| 服务 | 默认端口 | MySQL 连接额度 | 任务 |
| --- | --- | --- | --- |
| web | 5000 | 6 | 页面、普通列表查询 |
| orders | 5002 | 4 | 订单同步、自动面单、手工面单、采购物流任务、Yandex 订单同步 |
| stores | 5003 | 4 | 店铺链接同步与批量修改、禁售/侵权同步、信誉更新 |
| maintenance | 5004 | 2 | 商品成本、运费刷新、历史订单费用与图片补算 |
| worker | 5001 | 4 | 采集刊登、核重核价、WIPO、导出、通知与其他任务 |

后台端口仅监听 `127.0.0.1`，保留原有 HMAC 请求签名及业务权限检查。启动、状态、停止接口路由到同一任务所有者；误发到其他分组的签名任务请求返回 409。普通产品读取继续留在 Web。只有任务所属进程启动对应定时器，HTTP 的惰性启动钩子遵循相同归属。

每个进程的连接池、线程及锁相互独立，某一进程退出只对它退避重启，不中断其余服务。默认托管连接总预算是 20（不代表 MySQL 全实例上限）；启动前检查额度和端口冲突。数据库仍然共享 CPU、磁盘和行锁，拆进程不能隔离这些资源；默认同时降低店铺/详情/打印/成本计算并发，后续扩容需要实际混合负载测试，不能只提高连接数。其他脚本和 Yandex 独立服务的连接不计入此托管预算。

日志分别写入 `.logs/services/{web,orders,stores,maintenance,worker}.log`，可用 `BIT_SERVICE_LOG_DIR` 更改目录。后台 `/api/internal/worker-health` 需要签名，返回所属分组、PID 与连接额度，不触发业务任务。`restart_workbench.sh` 检查五个监听者均属于新管理进程才报告成功。

分组额度通过 `BIT_<GROUP>_DB_CONNECTIONS` 设置，总额度通过 `BIT_TOTAL_DB_CONNECTIONS` 设置。重型任务原有全局并发配置不会直接扩散给所有组，改用 `BIT_<GROUP>_<原配置名>` 显式覆盖，例如 `BIT_ORDERS_MERCADO_ORDER_PRINT_STORE_WORKERS=2`。端口默认相对 `BIT_WORKER_PORT` 递增，也可分别配置；launchd 配置需与重启命令的端口环境一致。

自动打印只对连接池获取失败的初始化阶段重试两次（等待 2、4 秒），发生在下载面单及扣费之前；不重放打印或扣费请求。已有订单打印记录、候选起始时间与业务幂等机制继续使用。失败仍会显示在订单同步状态中，并可在后续自动同步周期重新处理未成功订单。

验证包含：任务路由与签名、误发拒绝、定时器归属、资源总额、单组崩溃不重启其他组、自动打印初始化重试，以及重启脚本检查。未进行 1,000 店铺生产混合负载验收，也未通过测试触发实际面单扣费。

系统同时安装 LaunchDaemon 和同名 LaunchAgent 时，重启脚本优先沿用系统托管，校验同名用户托管属于本项目后卸载并停用它。仅停止本轮启动前捕获的旧 PID，由系统托管自动拉起新管理进程，不需要重新安装系统服务或管理员口令。各子进程共用 20 秒退出宽限期，超时只结束旧进程。

## 2026-10-08 页面重载查询与索引修复

线上诊断发现 Web 的 6 个连接持续排队；其中库存 SKU 店铺/站点下拉查询曾运行约 99 秒，售后订单上下文反复按店铺扫描订单 JSON。实时侵权 `/api/db/official-infractions/live` 及其 jobs/status 接口遗漏后台路由，也会在 Web 执行重型扫描。

本次改动：

- 库存下拉先通过现有 `idx_erp_meli_link_scoped_metadata` 覆盖索引按店铺、站点分组，只按主键读取每组一个名称，避免逐条读取商品大字段。缺少该索引时保留无 hint 的兼容路径。权限店铺条件仍在分组之前应用；同一店铺/站点名称取样本行，避免改名产生重复选项。
- 售后上下文拆成订单号、物流号、Pack 号三个索引查询，用 UNION 去重后读取详情。Pack 索引键截取到 64 字符，完整 JSON 等值条件继续校验，避免长值碰撞。未安装索引的旧数据库仍能执行相同 SQL。
- 订单按时间、采购成本排序时，选取分页 ID 不再关联四张汇率表；金额排序和汇总保留原有财务逻辑。
- 实时侵权启动和状态路由到 stores 进程；实时扫描遵循 `INFRACTION_STORE_WORKERS` 及共享同步预算，避免多个请求绕过后台并发上限。

独立维护入口（不会在页面请求中执行 DDL）：

```sh
python3 -m scripts.optimize_order_lookup_indexes
python3 -m scripts.optimize_order_lookup_indexes --apply
```

在当前 MySQL 8.0.42 数据库已建立 `idx_orders_token_created(token_id,date_created)`、`idx_orders_token_shipping(token_id,shipping_id)`、`idx_orders_token_pack(token_id,_pack_lookup_key)`。Pack 键为虚拟生成列，单独添加列后再添加索引，所有步骤使用 `ALGORITHM=INPLACE, LOCK=NONE` 和 5 秒元数据锁等待。MySQL 拒绝将虚拟列与索引合并为一个 LOCK=NONE 操作，因此拆分执行，没有使用共享锁或 COPY 降级。重复执行复用等价索引，并校验生成列表达式与类型。

实库单次测量（数据库查询耗时，不是浏览器完整重载时间）：库存旧查询在 15 秒上限被取消，新查询 1.221 秒、291 个店铺站点；同一店铺同组标识的售后补全 67.6ms → 0.9ms。近一个月订单 50 条分页含汇总约 1.062 秒，总数 6805；产品 50 条首页含总数约 0.236 秒，总数 1,686,531。执行计划确认物流号和 Pack 分支使用新索引。测量与索引执行计划保存在 `artifacts/page-query-optimization-20261008/`，只包含耗时、计数和计划，不保存订单详情。

索引已生效。代码需重载相应服务；检查旧 Web 的实时扫描是否结束后再切换，避免丢失进程内任务状态。现有订单路由综合测试中另有 7 项旧断言/模拟失败（旧页面文案、已有新增参数及采购物流权限模拟），不属于此次 SQL/索引改动；保留原用例未放宽断言。

## 2026-10-08 侵权查询内存修复

现场确认 5001 worker（旧 PID 43516）的物理内存足迹达到 24.1 GiB，大部分已被系统换出。通过本机 TCP 连接与 MySQL performance_schema 关联，发现该进程的侵权候选查询一次返回 1,688,531 条产品记录，包含 `source_snapshot_json` 等大字段。原结果接口先读取全量候选、复制列表、全量排序，最后才截取页面所需条数。

本次改为按主键递增每批最多 200 条读取，逐批校验内容哈希、规则版本和人工复核状态。提取当前标题、站点、账号和图片版本后丢弃原始快照，保留派生字段。有限结果请求使用有界排序，只保留请求的条数；筛选后总数和各风险状态汇总仍遍历全部数据计算，排序保持原来的稳定顺序。多来源候选的数量限制统一计算，跳过已完成记录后继续翻页。游标异常、查询失败和提前结束都会释放连接。

列表形式的候选和无限制导出最多物化 50,000 条；超出明确提示缩小范围后分批处理，不静默截断。完整状态校验仍需要扫描匹配数据，因此全库汇总可能较慢；此次不是全库查询延迟优化或所有业务路径的内存上限保证。

验证：

- 新增 9 项内存/分页测试；核心及相关服务回归 87 项通过。
- 扩展测试另有 7 项既存失败，以修改前的候选和结果函数复跑同样失败：2 项路由测试未隔离数据库，5 项旧规则断言与当前边界品牌/WIPO规则不一致。未改动这些断言。
