# 控制台并发调整（2026-09-22）

新版网页使用短请求跟踪本机 Agent 申诉任务，避免每个日志查看者长期占用一个 Waitress 工作线程。任务本身仍由 Agent 执行，无需重装 Agent。

## 行为

- 网页提交 `/api/run_shensu` 时带 `log_transport: "poll"`，接口入队后立即返回 JSON 和任务编号。
- `/api/run_shensu/<task_id>/events?after=<event_id>` 返回增量日志和任务状态。接口要求登录、申诉执行权限以及任务创建者身份；平台管理员可查看。
- 每页最多 200 个事件、约 512KiB 原始日志；单条历史大事件仍完整传送，避免丢日志。页面必须取完最后一页才显示结束。
- 正常日志刷新间隔 3–4 秒；隐藏页面暂停，切回后恢复。临时网络错误会以最长约 30 秒间隔退避重试，接着上次游标读取，不重新创建任务。
- 浏览器只保留最近 20 万字符，完整日志仍保存在服务端。此限制不会删除服务端历史。
- 旧网页、旧客户端保留原日志流协议。更新服务后，已有页面需要刷新才能使用短请求。
- 日常任务页状态刷新间隔约 4–5 秒；隐藏页面暂停自动请求，折叠日志停止自动读取，避免状态请求重叠。

数据库的 `_ensure_column` 对成功检查增加进程内缓存，以 PID、数据库连接目标、库名、表名、列名和定义隔离。默认 60 秒失效；检查/DDL 失败不会写入缓存。`MYSQL_SCHEMA_CHECK_TTL=0` 可关闭。此次没有跳过全部数据库迁移，也没有调整数据库连接上限。

## 上线与验证

修改 Python 服务代码后需重启现有控制台服务，再刷新浏览器。不要另外启动第二份控制台。重启前检查是否有服务器本机正在执行的人工任务；持久化的 Agent 队列不因重启删除。

本次针对接口、日志分页、权限、停止状态、浏览器断线恢复、数据库缓存和旧协议进行测试。另用临时 SQLite 队列和临时本地 HTTP 端口，验证 100 个待执行任务的日志请求能在 4 个 Waitress 工作线程下全部返回。该测试不触发真实 Agent、店铺或外部 API，不能替代 100 用户生产混合负载验收。

磁盘清理/扩容、拆分后台调度进程和数据库索引调整需要依据数据用途、查询计划及实际负载继续处理。不能把此次代码优化当作已完成全部容量建设。
