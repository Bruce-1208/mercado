# 业务员打印余额

业务员使用独立的打印账户。仓库人员生成订单面单时，系统从订单所属业务员的打印余额扣除每单 3 元；余额不足时，整批订单停止生成，提示充值。

## 充值与查看

- 新账户和现有尚未充值的账户，打印余额均为 0 元。
- 统一入口为「系统管理 → 支付管理 → 业务员打印余额」，可通过 `/billing?section=print-wallet` 直接打开；旧 `/print-wallet` 地址兼容跳转。超级管理员和企业管理员在该栏目登记已实际收到的充值款，填写金额和收款备注。企业管理员仅能为本企业登记；充值为人工登记，不会调用银行卡、微信或支付宝扣款。
- 业务员可以查看自己的余额、可打印订单数、充值和扣费流水。仓库等具备查看权限的人员可以查看本企业账户；普通业务员无权代充值或查看其他业务员的流水。
- 金额以整数分保存，300 分等于 3 元，不使用浮点数计算余额。
- 打印余额独立于账户订阅。订阅充值延长套餐有效期，不增加打印余额；打印充值不延长订阅期限。

## 计费规则

每次新的面单生成请求，对成功生成的每个订单收取 3 元。相同请求编号重试不会再次扣费；重新发起打印、补打使用新的编号，成功后再收取 3 元。一个订单的面单包含多页时，仍按订单计费。

这里的「打印」指系统成功生成并提供订单面单 PDF。网页无法确认实体打印机是否完成打印，因此关闭预览、取消浏览器打印或打印机缺纸，不会自动退款。

订单所属业务员从服务端的店铺国家站点设置读取，按企业和业务员账号/显示名称匹配。其他企业的同名业务员互不影响；同企业重名、未指定业务员、匹配不到唯一有效账户时，禁止扣费和生成，需先修正分配。仓库人员只可处理有权限的企业订单。

## 扣费、退款与重试

1. 服务端验证操作人的账号、角色、企业状态以及订单归属。
2. MySQL 事务锁定批次和涉及的业务员账户，检查整批所需余额。任一业务员余额不足时，全部回滚，尚未开始下载面单。
3. 余额足够时，先按每单 300 分预扣，并持久保存请求编号和各订单费用，再下载并合并面单。
4. 生成后按实际成功的订单结算，未生成的订单自动退回 300 分。全部失败时，全部退款。
5. 结算结果成功持久保存后，才向浏览器提供 PDF。结算重试不会重复退款。

请求和余额都保存在中心 MySQL 中，API 客户端使用相同流程。多业务员混合批次分别扣除各自余额，预扣操作具备整批事务一致性。充值和打印流水保留操作人、请求编号、订单号、金额及操作后余额。

支付管理的打印明细按订单展示订单号、店铺/站点、打印完成时间、执行打印人员的姓名/账号、费用和结果。姓名与身份、店铺资料在打印时留存，人员改名或订单店铺变更不改写已保存明细；退款记录同时显示原打印人员与退款操作人。批次部分失败时，各订单分别显示生成成功或失败退款。历史记录缺少店铺或身份快照时显示未记录，不按当前资料猜填；没有独立完成时间时使用已知结算时间并提示来源。可按订单号、流水日期、打印人员及类型筛选，分页查看全部记录。

如果请求中断，或生成后结算服务暂时不可用，系统保留已预扣记录，不在结果不明确时自动退款。原请求不会因重试重复扣费或再次下载；超级管理员或所属企业管理员核实后，可填写原因取消「待确认」请求并退回预扣金额。取消后的请求不允许再次结算或释放面单，重复取消不会重复退款，已经结算的请求不能取消。不要仅凭浏览器超时就立刻发起新的补打。

退款使用原预扣账户，即使业务员在生成期间被停用，也可退回原余额。业务员转移到其他企业后，旧企业钱包和流水不会向新企业人员显示，继续充值或扣费前需由管理员核对原余额归属。

自动订单同步完成后会检查未打印订单，按运单逐批校验业务员余额、预扣费用、下载官方面单并结算。系统使用独立的「系统自动打印」审计身份，不冒用人员账号；公开接口不能通过传入系统身份绕过账号校验。余额不足或业务员配置不完整时不扣费、不生成面单，保留候选供后续同步重试；一个运单失败不阻止其他运单打印。

首次启用默认回看最近 72 小时，之后保留启用起点以重试漏单。`MERCADO_ORDER_AUTO_PRINT_DISABLED=1` 仍可显式关闭自动打印。已打印、已结算成功以及扣费结果待确认的订单会排除，防止审计写入失败后再次收费；退款完成的失败订单可重试。每批 PDF 先持久化，再结算和记录成功，整轮合并失败仍保留已结算的分批面单。工作台公开接口及客户端提供订单面单时同样经过余额校验和结算流程。

## 启用与验证

服务端与 API 客户端需同步更新并重启。首次使用自动建立打印钱包、流水、请求和请求订单四张 MySQL 表；已有表会补充打印身份、店铺与完成时间快照字段，保留原有余额及流水。需要建表/补充字段权限及现有账号、角色、企业、订单与店铺站点设置表。上线前应先登记已收到的充值款，初始 0 元余额的业务员不能生成收费面单。

离线验证使用临时 SQLite 适配器和模拟面单生成器，覆盖金额精度、权限与企业隔离、归属歧义、整批余额不足、混合业务员扣费、失败退款、重复请求和事务回滚，不连接生产数据库或真实支付服务。SQLite 不能模拟 MySQL 的行级锁竞争，生产部署仍应在测试环境验证 MySQL 建表及并发扣费。

可直接运行新增的离线验证：

```bash
python3 -m pytest tests/test_print_wallet.py tests/test_print_wallet_routes.py -q
node --test tests/order_print_wallet.test.cjs
```
