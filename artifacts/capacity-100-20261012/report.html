实施内容

  1. 搜索、日期、采购平台及运费筛选只在临时结果建立时执行一次；后续统计、分页直接使用过滤后的结果，不再重复扫描搜索长文本。
  2. 收窄临时表字段，取消汇总无需的状态计算，并由已计算的实际运费判断缺失数量。
  3. 使用数据库 STORED 生成列保存完整 pack_id 文本，写入自动更新；保留大小写、长编号、空值和 LIKE 通配符的原有语义，不改为分词搜索。未迁移数据库会安全回退到原 JSON 查询。
  4. 每次完成账号和店铺授权后，同一组织的相同可见范围、筛选和分页共享查询结果；店铺权限、业务员、仓库或组织变化都会使用不同缓存。未知组织仍按账号隔离。缓存容量及 10 秒期限未扩大。

上线步骤与回退

代码已修改，生产库和运行中的服务尚未变更。搜索提速依赖生成列迁移。MySQL 添加 STORED 列需要 COPY 重建，会暂停表写入；应备份、预留一份表副本的磁盘空间，并在维护时段暂停订单写入及相关同步任务。迁移脚本默认仅检查，必须显式传入正确数据库名和 --apply 才会改表。

python -m scripts.optimize_order_search_projection --database 业务库名
python -m scripts.optimize_order_search_projection --database 业务库名 --apply

检查迁移结果后按现有流程部署并重启 Web 服务，再验证真实账号的列表、汇总、编号搜索与写入。回退可先恢复旧应用代码，生成列可以保留，不必立即再次重建表。请求路径不会自动执行这项 DDL。

测试配置与限制

  • 本机 MySQL 8，缓冲池 128 MiB；Web 32 线程、500 连接上限，数据库连接池 6。压测和被测服务同机。
  • 使用签名测试会话和真实账号查询 SQL；店铺授权映射来自测试夹具，未覆盖密码登录、完整生产鉴权链路、网络延迟及负载均衡。
  • 没有同时运行真实同步、刊登、消息、AI 生成等后台任务，也未验证一小时以上稳定性。正式容量承诺仍需在目标服务器加入这些负载验证。
  • 早期试压脚本误用了 Waitress 默认 100 连接上限，导致部分客户端无法接入。最终前后对比均已对齐项目实际默认 500；早期试压不作为最终收益证据。
  • 账号活跃模型在单次请求超过 5 秒时不会叠加新请求；因此必须结合实际请求/秒判断压力，不能只看虚拟用户数。
