# 泽顺控制台：100 人容量评估

检查时间：2026-09-22 21:08–21:12（北京时间）。对象为当前 Mac mini（192.168.1.11），包含本机控制台、MySQL 和公网 Cloudflare Tunnel。

## 结论

这台 M4 / 16GB 机器具有承担 100 个账号日常查询、店铺管理和任务调度的硬件基础，但当前实现不能作为“100 人同时使用全部功能”的可靠生产配置。最明确的瓶颈是申诉日志长连接占用有限的 Web 请求线程，其次是磁盘余量、后台任务和前台请求共用数据库连接预算。CPU 不是当前首要问题。

若 100 人同时运行浏览器自动化，应继续让各自电脑上的 Agent 执行；若大量浏览器、视频转码或本地模型集中在这台机器上，应分离执行节点，并另行按任务资源消耗测试。

本次仅进行了只读配置、系统、日志和数据库检查，以及少量登录页 GET 请求。没有修改服务配置、重启服务、启动业务任务或进行 100 人压测。以下容量判断是架构评估，不是压测认证。尚未确认每人的店铺数量、峰值活跃人数和任务组合。

## 最重要的调整

### 1. 先解决申诉日志占满请求线程

`bit/bit_interface.py:9678` 将本机 Agent 申诉返回为流式响应；`stream_local_agent_job`（9544 行）持续循环、每 0.5 秒读取事件和任务状态，直到任务结束。任务虽然在员工电脑运行，服务器上的日志请求仍长期占用一个 Waitress 工作线程。

因此接近 32 条同时活动的流式响应就可能占满整个工作线程池，普通页面、停止操作和 Agent 心跳开始排队。32 不是“可支持用户数”，其他请求也会占用线程。增加到 64 线程只能推迟问题。

优先方案：启动接口立即返回 job_id；浏览器通过 after_event_id 增量获取日志，任务运行时每 3–5 秒轮询，隐藏页面停止或显著降低频率，任务结束后停止。需要实时推送时，将 SSE/WebSocket 放到独立的异步推送服务，避免占用现有同步 Web 线程。

参考：[Waitress 请求线程机制](https://docs.pylonsproject.org/projects/waitress/en/latest/design.html)。

### 2. 释放和规划磁盘余量

先将可用空间恢复到至少约 50GiB，或维持 20%–25% 的余量，结合每天实际增量设置预警。检查备份、下载、模型和媒体缓存的用途与保留策略后再清理；本次看到本地 Ollama 模型目录约 15GiB，但没有删除任何内容。

MySQL 已将 binlog 保留设为 1 天，不能仅靠继续缩短保留来解决空间问题；需要核对备份和恢复要求。不要手工删除 MySQL 数据文件。数据库扩容、迁移或大表重建前应额外计算临时空间。应用 stdout/stderr 日志也需要轮转。

### 3. 限制后台并发，再调整数据库连接预算

后台同步、利润重算、订单补齐与前台 Web 请求目前同进程运行。为任务设置全局并发上限、队列、重复任务合并和外部 API 退避；避免每个用户发起一套不限量后台线程。

可将 Web 与后台执行拆分为独立进程，独立设置连接预算和保留前台容量。短期保留 Web 32 线程；日志改造完成、明确排队来自连接等待后，可以把单进程连接池从 12 试调至 16–24，并通过负载测试比较延迟、数据库 CPU、锁等待和超时。数值是起测范围，不是已验证配置。所有进程连接预算总和应显著低于 MySQL 上限并为维护、其他服务留余量；不建议直接把 max_connections 调成 500。

SQL 摘要显示，短窗口内对店铺 Token 和站点设置执行了数千次 SHOW FIELDS/SHOW COLUMNS 检查。应将结构迁移集中在部署/受控初始化阶段，避免正常请求反复检查和修补表结构。订单图片补齐、费用回填查询出现约 1.3–2.5 秒耗时，应结合真实筛选、EXPLAIN 和索引逐项优化；启动时冷缓存可能影响本次耗时。

### 4. 降低轮询、日志和队列放大

现有部分功能 1–2 秒轮询一次，有些刷新包含多个 API。估算公式是“活跃页面数 × 每轮接口数 ÷ 刷新间隔”，不是按账号数估算。

例如 100 个活跃页面，每 2 秒访问 2 个接口，即约 100 请求/秒；100 台 Agent 默认每 10 秒心跳一次，再增加约 10 请求/秒，尚未计入数据操作和日志上传。此例是负载模型，不是实测流量。

统一使用可见页面轮询、失败退避、随机抖动、避免上轮未完成又发下一轮；状态/日志合并请求、只传增量。Agent 日志批量写入，限制单批和历史返回量。

Agent 队列已使用 SQLite WAL，并非必须因“100 个账号”马上迁移。但 WAL 仍只有一个写入者，应保持事务短小、监控锁等待；多实例扩容或持续写入竞争时再迁移到共享 MySQL/其他集中队列。参考：[SQLite WAL 并发说明](https://www.sqlite.org/wal.html)。

### 5. 多进程扩容前先整理共享状态

程序存在 `_daily_tasks`、`_appeal_tasks`、`_live_infraction_jobs` 等进程内任务字典，以及进程内缓存和中心调度器。不能简单复制多个 Web 进程并轮询分流，否则可能出现任务状态查不到、停止请求找不到任务或重复调度。

先将任务状态持久化、明确调度器单实例职责，再进行多进程/多机扩容。不要为了关闭重复调度，在所有节点上全局关闭后台服务。

### 6. 公网与静态资源

检查员工实际网络到公网入口的延迟、上行带宽、错误率与重连。Cloudflare 日志中的本次启动前 connection refused 与源站尚未监听对应，不等于已证明隧道连接额度不足。

主页面模板源码约 1.6MB，可进一步按模块拆分脚本、缓存静态资源并确认压缩。模板源码大小并不是实际登录后响应大小，本次没有取得登录后页面传输量。

## 验收方式

在有代表性数据、隔离的测试任务和可控环境中，逐步进行 10 / 30 / 60 / 100 活跃用户测试，每档 15–30 分钟，最终混合负载至少连续 2 小时，并覆盖一个完整后台任务周期。分别覆盖商品和订单查询、100 条日志查看、100 台 Agent 心跳与日志上传、批量导出和同步。业务写入及外部 API 操作应使用测试数据或模拟，避免压测修改真实店铺。

建议验收目标（待业务确认）：常规查询 API P95 < 1 秒，公网常用页面/操作 P95 < 2–3 秒，失败率 < 0.5%，Agent 不因请求饥饿掉线，任务无重复执行；持续 CPU < 70%–75%，内存压力稳定、swap 不持续增长；无持续连接池耗尽、数据库锁等待堆积、SQLite locked 或 Web 队列增长。长任务完成时间单独按任务类型评估。

## 硬件与部署取舍

- 100 个账号、部分同时活跃、自动化在各自电脑：优先修复上述软件和磁盘问题，再验证现有机器，无需仅凭人数立即购买服务器。
- 100 人持续并发、持续增长的店铺与数据：将 Web、数据库、任务执行分离，并评估独立 Linux 环境；32GB 或以上内存、充足 SSD 可作为候选测试配置，最终按压测和增长量定型，不能凭配置承诺容量。
- 本机目前同时运行桌面浏览器、远程控制、Codex 和 Ollama 等程序。生产稳定性还取决于独占资源、网络、电源、备份恢复和变更方式，机器升级不能代替这些措施。

实施顺序：日志请求改造 → 磁盘余量 → 后台任务并发与数据库查询 → 轮询/缓存 → 100 用户验收 → 根据实测决定是否迁移或升级。
