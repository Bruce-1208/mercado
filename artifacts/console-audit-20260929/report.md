### F01 · P1：利润未扣平台手续费和实际运费，缺采购成本时仍显示高利润

**复现：**订单管理 → 打开打包单 `2000015260914351` → 查看费用和利润。

| 字段 | 页面显示 |
|---|---:|
| 订单金额 | USD 29.76 |
| 手续费 | USD 3.72 |
| 实际运费 | USD 12.76 |
| 结余 | USD 13.28 |
| 美元兑人民币汇率 | 6.703391 |
| 人民币收入 | CNY 199.49 |
| 采购成本 | CNY 0.00，采购订单未登记 |
| 利润 / 利润率 | CNY 199.49 / 100.0% |

**问题：**当前利润使用订单总额折人民币减采购成本，未扣页面已知的手续费和实际运费。仅将已展示的结余折人民币，就是 `13.28 × 6.703391 = 89.02` 元；页面利润比这一“扣平台费用后、扣采购成本前”的金额多了约 110.47 元。89.02 元也不能直接认定为最终净利润，因为采购等成本尚不完整。

**影响：**单笔判断、汇总利润、利润率及利润排序可能系统性偏高。未登记成本和真实零成本被混为一谈，容易让待采购订单显示 100% 利润率。

**代码核对：**[bit_mysql.py:3362](/Users/a11/mercado/bit/bit_mysql.py:3362)、[3390](/Users/a11/mercado/bit/bit_mysql.py:3390)、[3646](/Users/a11/mercado/bit/bit_mysql.py:3646)、[3748](/Users/a11/mercado/bit/bit_mysql.py:3748)分别涉及收入、单笔利润、汇总和排序。

**建议：**明确销售额、平台结余、预估利润、已核算利润四个口径；统一单笔/汇总/排序/导出公式。采购成本或关键费用缺失时显示“待核算”，单独统计核算覆盖率。退款、取消、费用币种和汇率日期也应进入统一口径。

**验收：**有费用、零费用、缺成本、退款和多币种样本均能对账；同一筛选条件下行明细与汇总一致。

证据：[订单详情文本](/Users/a11/mercado/artifacts/console-audit-20260929/order-detail.txt)、[详情截图](/Users/a11/mercado/artifacts/console-audit-20260929/order-detail.png)。

### F02 · P1：店铺链接的美客多分类筛选直接报错

**复现：**店铺链接 → 点击“全部美客多分类”。弹层显示 `names is not defined`，不能正常选择分类。

**根因已定位：**[index.html:27432](/Users/a11/mercado/bit/templates/index.html:27432) 在分类路径缺失的回退分支访问未定义的 `names`。现有 Node 用例 `unresolved categories remain selectable without an artificial site level` 同样失败，和真实页面现象一致。

**建议：**明确传入或局部构建分类名称映射；分类路径未同步时保留可选的分类 ID/名称，单项数据不完整不能使整个弹层失效。异常提示使用中文，并提供重试。

**验收：**完整路径、缺路径、缺名称、空分类四种情况均能打开和选择；相应用例通过。

### F03 · P2：订单汇率日期显示格式串，平台备注显示 null

**复现：**打开上述订单详情。两处汇率日期直接显示 `%Y-%m-%d`，平台备注显示 `null`。

**影响：**无法判断采用哪天汇率，影响对账可信度；空值暴露为技术字符串。

**排查线索：**[bit_mysql.py:3415](/Users/a11/mercado/bit/bit_mysql.py:3415) 与 [3443](/Users/a11/mercado/bit/bit_mysql.py:3443) 使用 `DATE_FORMAT(..., '%%Y-%%m-%%d')`，应核对 SQL 参数插值与百分号转义链路。本轮确认了展示异常，未进一步证明具体数据库执行分支。

**建议/验收：**有日期显示真实 `YYYY-MM-DD`，无日期显示“暂无”；`null`、空串、缺字段统一为空态。覆盖带参数及不带参数的查询路径。证据同 F01。

### F04 · P2：390px 窄屏布局与导航可访问性不合格

**复现：**订单管理，视口 `390 × 844`。

**实际：**文档宽 448px，超出视口；“拉取订单”四字逐字竖排；企业选择框被挤压，顶部右侧操作超出可见范围。导航只剩符号，多个按钮以同样的 `⚖` 或 `◎` 作为可访问名称，难以区分。

表格自身横向滚动可以接受；这里的问题是表格外的全局布局及操作入口也被挤坏。

**建议：**手机端使用带文字的抽屉导航；图标始终保留明确 `aria-label`；顶部下载/集成/账户操作收入菜单；筛选默认折叠；按钮禁止逐字压缩。移动订单优先展示状态、单号、金额和待办动作。

**验收：**390px 下页面外层无非预期横向溢出，关键操作不截断，读屏能识别每个导航目的。

**验收：**约定首屏耗时目标；故障注入时能进入可恢复的错误态，切换筛选不被旧请求覆盖。

## 3. 体验与管理建议

## 5. 建议处理顺序

1. **先修可信度与阻断项：**利润口径、分类选择器；修复后验证详情、汇总、排序和导出一致。
2. **再修每日使用问题：**产品列表加载、日期/空值、窄屏操作；补上异常态和数据缺失样本。
3. **补齐运行保障：**真实健康检查、角色权限矩阵、Agent/外部平台测试沙箱、自动化失败分类。
4. **最后优化界面：**压缩首屏说明、简化高级筛选、分步发布、统一业务文案和多币种标识。

建议以“登录 → 找订单 → 看费用 → 搜索/筛选 → 查商品 → 选分类”的只读链路作为每次发布必跑项；提交类链路使用专用测试账号和可清理的测试数据。
